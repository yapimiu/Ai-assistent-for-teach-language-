# Карта проекта для продолжения разработки через ИИ API

## Контекст
ROMÂNĂ B1 — персональный Telegram-преподаватель румынского для подготовки к B1, ILR по умолчанию. Python 3.12+, aiogram 3, FastAPI, PostgreSQL, SQLAlchemy 2, Alembic, Pydantic 2, OpenRouter. Модульный монолит. Milestone 1 реализован и проверен локально; реальные Telegram/OpenRouter и официальные материалы требуют отдельной проверки.

Прочитайте в порядке: `MASTER_PROMPT.md` → `AGENTS.md` → `ARCHITECTURE.md` → эту карту → `docs/VALIDATION.md` → `ROADMAP.md`. Исходные требования имеют приоритет над догадками модели. Не заявляйте о полной готовности B1 на основании короткой диагностики.

## Поток одного сообщения
1. aiogram принимает текст/inline-событие только из личного чата, идентичность берётся из Telegram sender.
2. Перед новой операцией транспорт пытается отправить сохранённые недоставленные ответы пользователя.
3. `LearningCore.handle(user_id, message_key, content)` берёт PostgreSQL advisory lock пользователя; повторный ключ возвращает сохранённый receipt.
4. Команда или ответ проходят через Learning Core в savepoint. При сбое модели учебная операция откатывается; известное использование модели сохраняется вне savepoint вместе с receipt.
5. Tutor передаёт модели только текущую задачу, ограниченную память и релевантные ошибки. Pydantic и проверка идентичности задачи валидируют ответ.
6. Прогресс/ошибки/состояние сохраняются, транзакция завершается. Только после этого Telegram получает текст; успешная доставка отмечается отдельно.

Не обещайте exactly-once доставку сообщений: возможен повтор после сбоя отправки. Exactly-once относится к учебным эффектам обработки одного ключа, не к внешнему HTTP-запросу при аварии процесса.

## Учебные инварианты
- confidence < 0.7 или is_acceptable=null: уточнение, без нового прогресса и выдуманных ошибок.
- Допустимы разные грамматически и смыслово корректные ответы.
- Освоение учебного задания требует двух уверенных самостоятельных ответов; явная подсказка исключает самостоятельность.
- После неопределённой оценки помощь остаётся учтённой для того же задания; сбрасывается при новом упражнении.
- Exam Mode скрывает подсказки и разбор до завершения; /mistakes и /progress не должны обходить это ограничение.
- Аудирование и говорение остаются непроверенными до голосового этапа.
- Все запросы и FK должны учитывать владельца. Нельзя принимать user_id из произвольного текста или callback payload.
- Переносы сохраняют историю и порядок зависимостей; конечную дату нельзя молча менять.
- Ни одна оценка LLM не является официальной оценкой ILR.

## Запуск и проверка
```bash
uv sync --frozen
cp .env.example .env  # только если собственного .env ещё нет
# Заполните реальные ключи безопасно; никогда не передавайте их ИИ.
docker compose up --build -d
```

Локально: настройте DATABASE_URL, выполните `uv run alembic upgrade head`, затем `uv run python -m app.bot`; API запускается через `uv run uvicorn app.api:app`. Подробнее и настройки прокси — README.md.

```bash
TEST_DATABASE_URL=postgresql+psycopg://user:password@localhost:5432/romana_test uv run --frozen pytest -q
uv run alembic check
```

Используйте отдельную тестовую базу. Без TEST_DATABASE_URL DB-тесты пропускаются. Последнее подтверждение: 38 тестов + 11 subtests, PostgreSQL 17; см. docs/VALIDATION.md. Не путайте mocks с живыми интеграциями.

## Как давать задачу внешней нейросети
Передавайте только нужные файлы и актуальный diff, не весь репозиторий и не .env. Модель через API сама по себе не имеет доступа к вашей файловой системе, Git или терминалу: клиент должен явно предоставить инструменты либо вы применяете патч и запускаете проверки самостоятельно.

Шаблон задания:

> Ты разработчик ROMÂNĂ B1. Прочитай приложенные AGENTS.md, ARCHITECTURE.md и PROJECT_MAP.md. Задача: [одна конкретная функция/ошибка]. Разрешённые файлы: [...]. Не изменяй архитектуру и другие этапы. Входные данные и ожидаемое поведение: [...]. Критерии приёмки: [...]. Сначала сообщи необходимые контракты, затем предложи патч и тесты. Не выдумывай API, официальные правила и результаты запуска. Если нет терминала — укажи команды, которые нужно выполнить человеку. Не запрашивай ключи в сообщениях.

Цикл: Architect определяет контракт → Coder делает ограниченный diff → человек/инструмент запускает тесты → независимый Reviewer получает diff и релевантный контекст → исправления → повтор затронутых проверок → обновление карты/ROADMAP → коммит. Не запускайте параллельное редактирование одинаковых файлов.

Нативные роли Codex: Architect gpt-6-astra/high, Coder gpt-6.1-sol/medium, Reviewer gpt-6.1-sol/high, Explorer gpt-6-luna/high. Эти имена подтверждены каталогом текущего Codex, но не гарантируют доступность в вашем внешнем API. Для другого провайдера используйте его реальные идентификаторы моделей и поддерживаемые настройки reasoning. `.codex` автоматически не настраивает сторонний API-клиент.

## Ближайшая работа
1. Ввести ключи и пройти реальный Telegram-цикл: регистрация → диагностика → план → два самостоятельных ответа → ошибки/практика → перезапуск.
2. Получить текущие официальные ILR PDF/страницы, обновить docs/ILR_SOURCES.md с точными источниками и датой. Не подменять сетевой отказ придуманными правилами.
3. На реальных ответах проверить педагогическое качество, выбор моделей и затраты. Расширять B1-программу по подтверждённым материалам; текущий набор тем — начальная программа.
4. При изменении схемы добавить новую миграцию и проверить upgrade/downgrade на одноразовой базе.
5. Только после приёмки Milestone 1 отдельно согласовать Calendar, голос и Anki. Интерфейсы уже отделены; самописная мультиагентная система backend не нужна.

## Секреты и публикация
`.env`, `.venv`, кэши исключены из Git. В коммите допустим только .env.example с пустыми API-ключами. Не отправляйте журналы с текстами учеников и ключами сторонним моделям. Публикация Git и публикация облачной среды — разные операции; черновик среды требует сохранения/публикации в её настройках.
